# AI Process Workflow (PM/CTO/PL/PA)

이 skill은 하네스의 공통 협업 절차(`docs/20-ai-process`, `docs/30-execution`, `docs/40-plan`, `docs/50-review`)를 Claude Code 세션에서 실제로 실행하는 방법을 정리한 것이다. 원칙 자체는 `docs/`가 단일 기준이고, 이 문서는 그것을 Claude의 subagent·hook·plan mode로 옮기는 실행 안내다. 원칙과 이 문서가 충돌하면 `docs/`가 상위 기준이다.

같은 Claude 세션이 하나의 요청을 단계별로 사고·보고하는 절차이지, 4개의 독립된 subagent를 항상 소환하라는 뜻이 아니다. 전문 관점이 실제로 필요할 때만 아래 "전문 subagent 확장" 절에 따라 별도 subagent를 추가한다.

## 역할 모델

| 역할 | 책임 | 하지 않는 것 |
|---|---|---|
| PM | 요청을 목표/범위/비범위/산출물/승인 지점으로 정리 | 구현 방식·라이브러리·아키텍처 확정 |
| CTO | 기술 적합성, 리스크(보안/성능/데이터/운영), 대안 검토 | PA 작업을 직접 쪼개지 않음 |
| PL | 재사용/공통화/작업 분리 설계, PA 산출물 1차 리뷰 후 통합 | 사용자 승인 없이 기술 방향 변경 |
| PA | 승인된 범위 안에서 실제 구현·검증 수행 | 범위 확장, 승인 없는 리팩터링 |

PM→PL(구현 내용 전달), PM↔CTO(기술 검토 요청은 PM뿐 아니라 PL도 발견 시 직접 요청 가능), PL→PA(작업 경계+검증 기준), PA→PL(변경/검증/blocker 보고) 순으로 단계식으로 소통한다. 한 역할 산출물이 끝났다고 사용자 확인 없이 바로 다음 역할로 자동 진행하지 않는다.

## 적용 강도

모든 작업에 4단계를 다 적용하지 않는다.

| 작업 유형 | 적용 |
|---|---|
| 단순 문서/한 줄 수정 | PA만, 필요시 PL 확인 |
| 구조 변경 없는 작은 코드 수정 | PM 간단 범위 정리 → PL 작업 경계 → 승인 → PA |
| 여러 파일/모듈 | PM 계획 → PL 계획(+필요시 CTO) → 승인 → PA |
| 아키텍처/보안 영향 | PM → CTO 상세 검토 → PL 분리 → 승인 → PA |

## 승인 게이트

**사용자 최종 승인 전에는 실제 구현(파일 생성/수정, 코드 변경, 설정 변경, 상태를 바꾸는 명령 실행)을 하지 않는다.** 계획 수립을 위한 read-only 탐색(관련 파일 읽기, 제한된 검색)은 허용한다.

이 게이트의 실행 수단은 Claude Code의 **plan mode**(승인 전 편집 차단, `ExitPlanMode`로 승인 요청)다. 단, plan mode는 자동으로 걸리는 게 아니라 **`EnterPlanMode` 도구를 직접 호출해야 진입**한다 — "적용 강도" 표에서 "단순 작업"이 아니라고 판단했다면, 채팅에 계획을 적는 것으로 끝내지 말고 반드시 `EnterPlanMode`를 호출해 실제로 그 상태에 들어간다(자세한 규칙은 `.claude/rules/process/01-workflow-gate.md` 참고). 별도 hook을 새로 만들지 않고 plan mode를 이 승인 게이트의 실행 수단으로 쓰되, 그 진입은 매번 능동적으로 호출해야 하는 행동이라는 점을 잊지 않는다. 다음은 승인이 필요한 항목이다.

- 작업 범위/기술 방향/아키텍처 확정
- 신규 의존성, 보안/인증/권한/배포 방식 변경
- 알려진 리스크·기술 부채 수용
- 계획에 없던 새 파일 추가, 범위 밖 파일 수정

승인 상태는 **승인 / 거부 / 보류 / 재요청** 중 하나로 판단한다. 거부·재요청이면 반려된 단계(PM/CTO/PL)가 다시 제안하고, PA는 새 지시 없이 임의 재진행하지 않는다.

## 보고 형식

복잡한 작업: PM 계획 → CTO 검토 → PL 계획 → PA 작업 분리 → 승인 요청 → 실행 결과 → 검증 결과 → 남은 리스크 순으로 보고한다.

작고 리스크 낮은 작업은 아래처럼 간소화하고 생략 이유를 짧게 남긴다.

```md
## 간소화 보고
- PM: 범위가 단일 문서 수정으로 제한됨
- CTO: 기술 위험 없음
- PL: 작업 분리 불필요
- PA: 처리 완료
```

승인 요청 형식:

```md
## 사용자 승인 요청
- 결정할 내용:
- 추천 방향:
- 대안:
- 리스크:
- 승인 후 실행할 작업:
```

## 작업 분리(병렬 실행)

PA는 기본적으로 다중 subagent(`Agent` 도구)로 실행한다. 여러 PA로 나눌 때는 파일 영역이 다르거나, 조사/설계/실행/검토가 독립적인 경우에만 분리한다. 같은 파일을 동시에 건드리거나, 설계가 아직 승인되지 않았거나, 통합 비용이 실행 비용보다 크면 나누지 않는다.

PL 역할이 담당 범위·읽기 대상·검증 기준·통합 순서를 먼저 정하고, 각 PA 산출물을 받아 최종 소스를 직접 확인한 뒤 검증·통합까지 책임진다. PA는 자기 작업 결과를 현재 디렉토리에 직접 통합하지 않는다.

## PA 완료 전 Reviewer 검토 (필수)

@.claude/rules/process/02-agent-review.md 를 따른다. PA는 완료 반환 전에 reviewer를 동기 호출하고, 지적사항 수정·검증·재검토 후 PASS 최종본만 PL에 전달한다. BLOCKED는 완료와 구분한다. `.claude/hooks/check-pa-review.cjs`는 종료 보고 누락을 검사하며 실제 호출·검토 품질을 인증하지 않는다.

작업 중 대화에 프롬프트·MD 개선 필요가 있으면 @.claude/agents/prompter.md 를 호출한다. MD 변경은 사용자 검토 승인 후 담당 실행자가 반영하며, 아래 리뷰 기록도 같은 승인 요건을 따른다.

## PA 완료 콜백 보고 (필수)

PA(서브에이전트)가 종료되면 `.claude/hooks/subagent-stop-flag.sh`(`SubagentStop` 훅)가 플래그를 남기고, 메인 세션이 응답을 끝내려는 순간 `.claude/hooks/check-pa-callback.sh`(`Stop` 훅)가 이를 감지해 응답 종료를 막는다. 이 덕분에 PA 종료 시점을 사용자가 놓치지 않는다 — 훅이 막으면 아래 형식으로 콜백 보고부터 출력한 뒤 계속한다.

**성공 시**

```md
✅ PA 작업 완료
📁 변경/생성 파일: ...
📝 작업 내용: ...
🧪 검증 결과: ...
🔎 Reviewer 검토: 검토 기준·범위·최종 PASS, 지적사항별 추천
🔁 추천 처리: PA 수정·재검증, PL 수용/보류 결정·이유 (없으면 없음)
```

**실패 시**

```md
❌ PA 작업 실패
💥 실패 이유: ...
🔍 에러 분석: ...
🔎 Reviewer 검토: BLOCKED 사유, 수행한 검토 또는 미수행 사유, 미해결 지적사항
🔁 다음 조치: (PL이 원인 검증 후 PA 재작업 지시 / 🧭 CTO 에스컬레이션(기술 이슈) / 🗂️ PM 에스컬레이션(설계·범위 이슈) / ❓ 사용자 확인 필요 항목)
```

실패는 보고로 끝내지 않는다. PL이 실패 사유를 직접 검증하고, 기술적 원인이면 CTO 역할과, 설계·범위 문제면 PM 역할과 소통해 방향을 정한 뒤 PA에게 재작업을 지시하고 **성공할 때까지 반복**한다. 사용자 판단이 필요한 지점이 생기면 그때 사용자에게 질문한다.

이 훅은 SubagentStop payload의 공식 필드 `agent_type` 값이 `pa`인 경우에만 플래그를 남긴다. 따라서 PM/CTO/PL이나 리서치/탐색(Explore 등) 서브에이전트가 끝났을 때는 이 콜백이 걸리지 않는다 — 그런 경우에는 평소처럼 요약만 하고 넘어간다.

(과거에는 `pa.md` 본문의 HTML 주석 마커를 서브에이전트 transcript에서 grep하는 방식이었으나, 대화에서 마커 문자열을 인용만 해도 오탐이 발생해 공식 필드 기반으로 교체했다.)

## 리뷰·오류 기록

에러(재현 가능한 실패), 크리티컬(보안/데이터손실/배포실패/장애 가능성), 개선사항(품질/유지보수성)을 발견하면 숨기지 않고 기록한다.

기록 위치, 디렉토리 분류, 파일 네이밍, 상태 표기(`[ ]`/`[x]`/`[-]`) 기준은 `docs/50-review/04-review-logging.md`를 따른다. 프로젝트에 자체 리뷰 로그 규칙(예: `.ai/reviews/README.md`)이 있으면 그것을 우선한다. critical 항목은 사용자 승인 없이 resolved 처리하지 않는다.

## 기술 규칙과의 관계

Spring/naming 등 일반 기술 원칙은 이 문서가 다시 정의하지 않는다. 프로젝트가 가진 `.claude/rules/*`가 더 구체적이면 항상 그것을 우선한다.

## 역할별 subagent

PM/CTO/PL/PA는 각각 `.claude/agents/pm.md`, `cto.md`, `pl.md`, `pa.md`로 실제 subagent로도 존재한다. `Agent(subagent_type: "pm" | "cto" | "pl" | "pa", ...)`로 직접 호출할 수 있다.

- 가벼운 작업은 이 문서의 절차를 메인 세션이 그대로 따르는 것으로 충분하다(별도 subagent 소환 불필요).
- 독립된 컨텍스트에서의 검토(예: CTO 관점의 2차 의견), 또는 PL이 여러 PA를 실제로 병렬 실행해야 하는 경우에는 위 subagent들을 직접 호출한다.
- PL subagent는 `Agent` 도구를 가지고 있어 PA subagent를 스스로 실행·통합할 수 있고, 필요하면 CTO/PM subagent도 호출해 에스컬레이션할 수 있다.

## 전문 subagent 확장

보안 리뷰어, DBA, 인프라 아키텍트, 성능 리뷰어처럼 **특정 전문 관점과 판단 책임**이 반복적으로 필요해지면 그때 `.claude/agents/<role-name>.md`로 별도 전문 subagent를 추가한다. 필요가 확인되기 전에 선제적으로 만들지 않는다.
