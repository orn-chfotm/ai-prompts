# 작업 시작 전 워크플로우 게이트 (필수)

이 문서는 승인 게이트의 **Claude 전용 구체 문법**(`EnterPlanMode` / `ExitPlanMode`, subagent 호출)을 담당한다. tool 중립 원칙("승인 게이트는 선언이 아니라 도구로 강제한다")은 `docs/20-ai-process/agents/03-approval-authority.md`가 담당하며, 이 문서는 그 원칙을 Claude Code에서 실제로 실행하는 방법만 정의한다.

`.claude/skills/ai-process-workflow/SKILL.md`의 "적용 강도" 표에서 **"단순 문서/한 줄 수정"을 제외한 모든 등급**(구조 변경 없는 작은 코드 수정 포함)은, 요청이 아무리 구체적이고 작아 보여도 곧바로 Edit/Write로 들어가지 않는다. "파일 하나만 고치면 된다"는 판단은 이 게이트를 건너뛸 근거가 되지 않는다 — 등급표의 "구조 변경 없는 작은 코드 수정"도 승인이 필수인 등급이다.

## 적용 방식

메인 세션이 혼자 PM/CTO/PL 내용을 지어내지 않는다. **실제 PM/CTO/PL/PA subagent 체인**을 쓴다.

1. 메인 세션이 read-only 탐색을 먼저 한다.
2. `Agent(subagent_type: "pm")`을 호출해 목표/범위/비범위/산출물을 정리시킨다.
3. `Agent(subagent_type: "cto")`를 호출해 기술 리스크·스키마·함정 여부를 검토시킨다(단순 리스크 없는 작업이어도 "리스크 낮음" 판단 자체는 CTO 산출물로 받는다).
4. PM/CTO 산출물을 받아서 `EnterPlanMode`로 정지하고, 그 내용을 "plan 문서 형식"(아래 섹션)에 맞춰 plan 파일에 정리해 `ExitPlanMode`로 사용자 승인을 받는다.
5. 승인 후, `Agent(subagent_type: "pl")`을 호출해 승인된 plan을 전달하고 작업을 PA 단위로 쪼개게 한다. PL subagent는 `Agent` 도구가 있어 스스로 `Agent(subagent_type: "pa")`를 (파일 영역이 겹치지 않으면) 여러 개 병렬로 소환해 실행시키고, 산출물을 리뷰·통합한 뒤 메인 세션에 최종 보고한다.
6. 메인 세션은 PL의 최종 보고를 사용자에게 전달한다. PA 콜백 보고 형식(성공/실패 아이콘)은 `.claude/skills/ai-process-workflow/SKILL.md`의 "PA 완료 콜백 보고" 절을 그대로 따른다.

"단순 문서/한 줄 수정" 등급만 이 체인 없이 메인 세션이 바로 처리한다.

## 규칙

- 작업을 시작하기 전에 "적용 강도" 표를 기준으로 이 작업의 등급을 먼저 판단하고, 그 판단을 사용자에게 명시한다.
- "단순 문서/한 줄 수정"이 아니라면, 실제 코드 수정(Edit/Write) 전에 위 "적용 방식" 절차대로 `pm`/`cto` subagent를 호출해 산출물을 받고, 그 내용을 plan 문서에 담아 제시한다. 메인 세션이 PM/CTO 판단을 대신 지어내지 않는다.
- "요청이 이미 구체적이다", "파일 하나뿐이다", "기존 메서드를 재사용하니 리스크가 낮다"는 이유로 이 단계를 생략하지 않는다 — 요청의 구체성/작업 크기와 승인 절차는 별개다.
- 제시한 뒤에는 사용자 승인(또는 명시적 진행 지시)을 기다린 뒤에만 Edit/Write를 시작한다.
- 사용자가 "계속 진행해"처럼 명시적으로 승인하면, 직전에 제시한 PM/CTO/PL 요약의 가정(assumption)들은 승인된 것으로 보고 진행한다. 단, 사용자가 특정 가정을 지적/정정하지 않았다는 것이 "그 가정이 확정됐다"는 뜻은 아니므로, 구현 중 근거가 흔들리면 다시 확인을 요청한다.

## plan 문서 형식

plan mode에서 작성하는 plan 파일은 PM/CTO/PL 내용을 하나의 글로 뭉뚱그리지 않는다. 역할별로 섹션을 나눠서 사용자가 각 역할의 판단을 구분해서 읽을 수 있게 한다 — 승인은 한 번(`ExitPlanMode`)에 받더라도, 그 안의 내용은 역할별로 분리해서 보여준다.

- `## PM 요약`: 목표/범위/비범위/산출물. 이 작업이 뭘 하는 건지, 뭘 하지 않는지.
- `## CTO 검토`: 기술적 리스크, 스키마/함정 여부, 대안이 있었다면 그것. 리스크가 낮은 작업이면 "리스크 낮음 — 이유"만 짧게 적어도 된다(생략은 하지 않는다).
- `## PL 작업 경계`: 어떤 파일/레이어를 건드리는지, 기존 어떤 패턴/유틸을 재사용하는지, 작업 순서.
- 이 세 섹션 뒤에 필요하면 `## 구현 범위`(파일별 상세 변경 내용)와 `## 검증`(테스트/빌드 확인 방법)을 이어서 적는다.
- "단순 문서/한 줄 수정"처럼 plan mode 자체를 안 타는 등급에는 이 형식이 적용되지 않는다.

이 형식은 `docs/40-plan/01-plan-structure.md`의 "역할별 섹션 구조" 권장 형식과 같다.

## 기술적 강제 수단 (필수 — 채팅 텍스트만으로는 이 게이트를 지킨 것이 아니다)

"단순 문서/한 줄 수정"이 아니라고 판단했다면, 메인 세션 혼자 PM/CTO 판단을 채팅에 적는 것으로 끝내지 않는다 — 실제 `pm`/`cto` subagent를 호출해 받은 산출물을 **반드시 `EnterPlanMode` 도구를 호출해 실제로 plan mode에 진입**한 뒤 plan 문서에 담고, `ExitPlanMode`로 사용자 승인을 받은 뒤에만 (PL subagent 호출 → PA subagent 실행으로) 다음 단계를 시작한다.

- "먼저 범위를 정리하겠습니다"/"바로 반영하겠습니다"라고 말만 하고 같은 턴에 바로 파일을 읽고 Edit로 들어가는 것은 게이트를 지킨 게 아니다 — plan mode에 실제로 진입하지 않으면 Edit/Write를 막는 harness 차원의 장치가 전혀 없기 때문에, 스스로의 판단(자기 다짐)에만 의존하게 된다. 세션이 승인 확인 없이 진행하는 모드여도 `EnterPlanMode` 호출 자체는 harness가 Edit/Write를 차단하므로 이게 유일하게 신뢰 가능한 강제 수단이다.
- 즉, "단순 문서/한 줄 수정이 아니다"라고 판단한 순간 다음 도구 호출은 (read-only 탐색이 아직 안 끝났다면 탐색을 마친 뒤) `EnterPlanMode`여야 한다. 예외 없음.

## 반복된 위반 패턴

아래는 이 게이트가 만들어진 근거다. 전부 실제로 발생했고, 일부는 게이트를 만든 **직후 같은 세션에서 곧바로 반복**됐다. 즉 "이번엔 안 그러겠다"는 다짐으로는 막히지 않는다는 것이 확인된 패턴이다.

1. 여러 계층(entity/dto/repository/service/controller)과 스키마 제약까지 건드리는 작업에서, 요청이 구체적이라는 이유로 PM/CTO 단계 없이 바로 구현에 들어감.
2. "범위부터 정리하겠다"고 채팅에 적고도 `EnterPlanMode`를 호출하지 않은 채 같은 턴에 곧바로 여러 파일을 Edit함.
3. "단일 파일이고 기존 메서드를 재사용하니 낮은 리스크"라고 스스로 판단하고 승인을 기다리지 않고 실행함 — 등급표상 "구조 변경 없는 작은 코드 수정"도 승인이 필수인데도.

세 패턴 모두 공통점은 하나다: 판단 후 다음 행동이 **말**이었고 `EnterPlanMode` **호출**이 아니었다는 것. "이번 건 작아서 괜찮다"는 예외를 스스로 만들지 않는다.
