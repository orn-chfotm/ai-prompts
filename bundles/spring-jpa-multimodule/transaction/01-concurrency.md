# Transaction / Concurrency 규칙

이커머스에서 주문과 재고는 동시성 정책 없이 구현하지 않는다.

## Service 트랜잭션

- 조회 전용 메서드는 `@Transactional(readOnly = true)`를 사용한다.
- 상태 변경 메서드는 `@Transactional`을 사용한다.
- 트랜잭션 경계는 Service에 둔다.
- Controller나 Repository에서 비즈니스 트랜잭션을 관리하지 않는다.

## Entity 상태 변경

- setter 대신 의미 있는 메서드로 상태를 변경한다.
- 상태 변경 전 필요한 검증은 Entity 메서드 또는 Service 정책으로 명확히 둔다.

```java
product.removeStock(quantity);
order.cancel();
```

## 재고 차감

주문/결제와 연결된 재고 차감은 **비관적 락**(`@Lock(LockModeType.PESSIMISTIC_WRITE)`)을 기본 전략으로 사용한다.

- 이유: 낙관적 락(`@Version`)은 충돌 시 예외를 던지고 재시도를 애플리케이션에 위임하는 구조다. 이미 결제가 완료된 주문 건의 재고 차감이 낙관적 락 충돌로 실패하면, 실패한 재시도 끝에 결제를 되돌려야 하는데 이는 허용되지 않는다.
- 비관적 락은 충돌 시 예외 대신 대기 후 순차 처리되므로 "결제는 완료, 재고 차감은 실패"라는 불일치 상태를 만들지 않는다.
- 낙관적 락, 조건부 update는 결제와 무관한 저경합 갱신(예: 관리자 재고 수기 조정)에 한해 예외적으로 허용한다.
- 한 트랜잭션에서 여러 SKU/상품을 잠글 때는 id 오름차순 등 일관된 순서로 락을 걸어 데드락을 방지하고, 락 대기 타임아웃을 명시적으로 설정한다.

동시 요청에서 재고가 음수가 되거나 초과 판매가 발생하면 안 된다.
재고 정책이 정해지지 않은 상태에서 주문 기능을 확장하지 않는다.

## 주문 생성

- 중복 주문 방지가 필요한 endpoint는 멱등성 키를 고려한다.
- 결제/외부 API 호출이 생기면 트랜잭션 내부에서 오래 대기하지 않도록 분리한다.
- 주문 생성 실패 시 재고, 주문 상태, 결제 상태가 불일치하지 않도록 보상 흐름을 설계한다.

## 외부 시스템 호출

DB transaction 안에서 외부 API를 오래 호출하지 않는다.
필요하면 상태 저장 후 비동기 처리 또는 별도 단계로 분리한다.
