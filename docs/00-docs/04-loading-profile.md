# 로딩 프로파일

이 문서는 하네스 문서를 **항상 로드하는 코어**와 **필요할 때만 로드하는 선택 문서**로 나누는 기준을 정의한다.

모든 프로젝트가 모든 문서를 로드하지 않는다. JavaScript를 쓰지 않는 프로젝트가 JavaScript 규칙을 매 세션 로드할 이유가 없고, Spring을 쓰지 않는 프로젝트가 Spring 상세 규칙을 로드할 이유도 없다.

## 코어

코어는 tool과 기술 스택에 무관하게 항상 로드하는 문서다. 역할 모델, 승인 절차, 실행 흐름, plan 구조, 리뷰 기준이 여기 해당한다.

| 범위 | 내용 |
|---|---|
| `docs/00-docs/*` | 문서 구조, 하네스 경계, dir init, 로딩 프로파일 |
| `docs/20-ai-process/**` | 역할 모델, 승인 권한, 역할별 기준서 |
| `docs/30-execution/*` | 업무 흐름, 작업 분리, 출력 형식 |
| `docs/40-plan/*` | plan 구조, 소통 구조, 코드 산출 구조 |
| `docs/50-review/*` | 리뷰 절차, 테스트 정책, 오류 처리, 리뷰 로깅 |

하네스의 Claude 진입점(`CLAUDE.md`)은 이 코어만 import한다.

## 선택 로드

다음은 프로젝트가 필요할 때만 로드한다.

| 범위 | 내용 | 로드 기준 |
|---|---|---|
| `docs/10-technical/*` | naming, Spring, JavaScript 등 스택별 **추상 원칙** | 해당 스택을 쓰는 프로젝트만 |
| `bundles/<name>/` | 스택별 **상세 규칙 묶음** | 해당 스택을 쓰는 프로젝트만 |

`10-technical`의 문서를 삭제하지는 않는다. 코어 import 목록에서만 빠졌을 뿐, 선택 로드 대상으로 그대로 유지한다.

## 프로젝트에서의 연결

### Claude

프로젝트 루트 `CLAUDE.md`에서 필요한 것만 import한다.

```md
@.ai-prompts/CLAUDE.md                                   ← 코어 (필수)
@.ai-prompts/bundles/spring-jpa-multimodule/00-index.md  ← 스택 번들 (선택)
@.claude/rules/...                                       ← 프로젝트 고유
```

- 첫 줄(코어)은 항상 유지한다.
- 스택 번들 줄은 그 스택을 쓰는 프로젝트만 추가한다.
- 프로젝트 고유 rule, skill은 그 아래에 둔다.

### Codex

Codex의 `AGENTS.md`에는 `@import` 문법이 없다. 대신 참조 문서 목록으로 같은 효과를 낸다.

스택 번들을 쓰려면 `AGENTS.md`의 참조 문서 목록에 번들 index 경로를 한 줄 추가한다.

```md
## 스택 번들 참조

- bundles/spring-jpa-multimodule/00-index.md
```

이 목록은 자동 로드 대상이 아니라, 작업 중 필요할 때 읽어야 하는 문서 안내다.

## 새 번들 추가 규칙

새 스택 번들은 다음 기준으로 만든다.

- 위치는 `bundles/<name>/`이고, 진입점은 `bundles/<name>/00-index.md`다.
- `00-index.md`가 자기 하위 문서를 import하거나 참조 목록으로 안내한다. 프로젝트는 index 한 줄만 연결하면 된다.
- `00-index.md` 상단에 적용 대상 스택을 명시한다. 어떤 프로젝트가 이 번들을 로드해야 하는지 판단할 수 있어야 한다.
- `00-index.md` 상단에 이 번들이 **예시이자 참고용**이라는 성격을 함께 명시한다.
- 번들 문서에는 `docs` 코어의 원칙을 다시 정의하지 않는다. 충돌이 생기면 `docs` 코어가 상위 기준이다.

## 번들 사용 시 주의

번들에는 그 번들을 만들어낸 특정 프로젝트의 고유 결정이 섞여 있을 수 있다.

- 디렉토리명, 모듈명, 패키지 경로, 테이블명 같은 값
- 그 프로젝트에서만 성립하는 계층 분리 방식
- 그 프로젝트의 배포 구조에 맞춘 설정

따라서 번들을 그대로 복사해 적용하지 않는다. 자기 프로젝트의 실제 구조를 먼저 확인하고, 번들은 참고 기준으로 사용한다.

번들 내용과 실제 프로젝트 구조가 다르면 번들이 아니라 실제 프로젝트 구조를 따르고, 필요하면 프로젝트 고유 rule로 따로 기록한다.
