# Plan 구조

작업 plan은 역할별 판단이 이어질 수 있도록 작성한다.

## 표준 구조

```md
## 작업 Plan

- 요청 요약:
- 목표:
- 범위:
- 비범위:
- 승인 필요 지점:
- 기술 검토 항목:
- 개발 작업 경계:
- PA 작업 단위:
- 검증 기준:
- 예상 리스크:
```

## 역할별 섹션 구조 (권장)

승인은 한 번에 받더라도, plan 문서의 내용은 역할별로 나눠 쓴다. 하나의 글로 뭉뚱그리면 사용자가 어느 판단이 PM 것이고 어느 판단이 CTO 것인지 구분할 수 없다.

아래 형식을 권장 형식으로 사용한다.

```md
## PM 요약

- 목표:
- 범위:
- 비범위:
- 산출물:

## CTO 검토

- 기술 리스크:
- 함정 또는 제약:
- 검토한 대안:

## PL 작업 경계

- 건드리는 파일/레이어:
- 재사용할 기존 패턴/유틸:
- 작업 순서:

## 구현 범위

- (파일별 상세 변경 내용)

## 검증

- (테스트, 빌드, 확인 방법)
```

### 작성 기준

- `## PM 요약`은 이 작업이 무엇을 하고 무엇을 하지 않는지 드러낸다.
- `## CTO 검토`는 리스크가 낮은 작업이어도 생략하지 않는다. "리스크 낮음 + 그 이유"를 한 줄이라도 적는다. 생략은 검토하지 않은 것과 구분되지 않기 때문이다.
- `## PL 작업 경계`는 PA가 그대로 실행할 수 있을 만큼 파일 범위와 순서를 구체적으로 적는다.
- `## 구현 범위`와 `## 검증`은 필요할 때 이어서 적는다.

위 "표준 구조"는 항목 체크리스트로 계속 유효하다. 역할별 섹션 구조는 그 항목들을 역할 단위로 묶어 제시하는 권장 형식이다.

## 역할별 입력

- PM: 목표, 범위, 비범위, 승인 지점
- CTO: 기술 방향, 제약, 리스크, 대안
- PL: 작업 경계, 재사용성, 공통화, 검증 기준
- PA: 실행 결과, blocker, 검증 결과

## 원칙

Plan은 실행 중 바뀔 수 있지만, 사용자 승인이 필요한 변경은 새 승인 요청으로 분리한다.
