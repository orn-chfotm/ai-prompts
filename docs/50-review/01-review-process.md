# 리뷰 절차

리뷰는 변경의 정확성, 범위 준수, 기술 안정성, 검증 가능성을 확인한다.

## 역할별 리뷰

- PA: 구현·검증 종료 단계에 Reviewer를 요청하고, 지적사항을 직접 수정·검증한 뒤 재검토를 받는다.
- Reviewer: 프로젝트 MD·코드베이스 규칙을 읽기 전용으로 검토한다. 코드를 직접 수정하지 않고 PA에 재작업을 요청한다.
- PL: Reviewer PASS인 최종 변경본과 지적사항별 처리 근거를 받아 통합 리뷰를 수행하고, 작업 경계, 통합 충돌, 재사용성, 공통성 위반 여부를 확인한 뒤 PA 작업 결과를 현재 디렉토리에 통합한다.
- CTO: 기술 방향, 보안, 성능, 데이터, 운영 리스크를 확인한다.
- PM: 요청 목표와 산출물이 맞는지 확인한다.
- 사용자: 최종 승인, 거부, 보류, 재요청을 결정한다.

## Reviewer 완료 게이트

PA → Reviewer → PA 수정·재검토 → PL 순서로 진행한다. 최종 변경본의 PASS 이전에는 완료본으로 전달하지 않는다. 호출 불가, 미해결 필수 수정, 승인 필요 사항은 BLOCKED로 보고하고 다음 조치를 명시한다. 실제 검토 없이 통과로 보고하지 않는다.

PASS 후 코드가 바뀌면 통합 단계에서도 재검토한다. 선택적 개선의 미반영 이유와 리스크 수용에 필요한 사용자 승인을 구분한다. 상세 역할과 결과 형식은 `../20-ai-process/agents/roles/06-reviewer.md`를 따른다.

## 리뷰 기준

- 승인된 범위 안에서 작업했는가?
- 불필요한 변경이 섞이지 않았는가?
- 테스트 또는 검증 결과가 명확한가?
- 남은 리스크가 사용자에게 보고되었는가?

## PL 1차 코드 리뷰 기준

PL은 PA 산출 코드를 통합하기 전에 다음을 확인한다.

- PA가 지정된 분리 작업 컨텍스트에서 작업했는가?
- PA가 현재 디렉토리에 직접 통합하지 않았는가?
- PA가 승인된 작업 범위와 파일 경계를 지켰는가?
- 코드가 기존 구조, naming, 스타일, 테스트 패턴과 일관적인가?
- 재사용 가능한 기존 코드나 공통 모듈을 무시하지 않았는가?
- 작업 단위가 리뷰 가능한 크기와 목적을 유지하는가?
- 테스트 실패, 미검증 항목, blocker가 숨겨져 있지 않은가?
- error, critical, improvement로 기록할 항목이 있는가?

PL 리뷰에서 범위 밖 변경, 아키텍처 판단, 보안 또는 데이터 리스크가 발견되면 CTO 검토로 에스컬레이션한다.

## PL 통합 검증 기준

PL은 PA 산출물을 현재 디렉토리에 통합한 뒤 다음을 확인한다.

- 통합 충돌이 없거나 해결 내용이 PA 작업 범위 안에 있는가?
- 현재 디렉토리에서 필요한 테스트 또는 검증을 다시 수행했는가?
- PA 작업 결과의 변경이 의도한 결과만 포함하는가?
- 검증 후 PA의 분리된 작업 영역을 정리했는가?

통합 후 검증에 실패하면 PL은 PA 작업을 현재 디렉토리에 확정하지 않고 원인을 분류해 PA 재작업, PL 재분리, CTO 검토, 사용자 승인 요청 중 하나로 되돌린다.

## 리뷰 기록

리뷰 중 다음 항목이 발견되면 `04-review-logging.md` 기준에 따라 기록한다.

- 에러: 실제 실패, 오류, 재현 가능한 문제
- 크리티컬: 보안, 데이터 손실, 배포 실패, 장애 가능성이 큰 문제
- 개선 사항: 당장 실패는 아니지만 품질, 유지보수성, 테스트 안정성을 높이는 항목

기록 위치는 이 하네스 문서 submodule 내부가 아니라, 하네스를 가져간 실제 프로젝트 내부여야 한다. 리뷰 결과는 우선 대화로 보고하며, MD 기록 생성·수정과 구성 변경은 구체적인 변경안에 대한 사용자 승인 후 담당 실행자가 반영한다. Reviewer와 Prompter는 직접 파일을 수정하지 않는다.
